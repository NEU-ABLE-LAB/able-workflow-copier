# Inspiration

The ABLE Workflow was inspired by two broad kinds of projects. The first is **workflow templates**: projects that show how a template can lower the barrier to starting with a better repository structure, clearer packaging, stronger documentation, and a more reproducible workflow from the beginning. The second is **real Snakemake workflows**: projects that show which development practices hold up under real scientific, data-engineering, and HPC constraints. Together, good examples of both suggested that a useful template should be explicit about workflow orchestration, reusable Python packaging, tabular data contracts, automated checks, and updateable project scaffolding.

## Workflow templates

Workflow templates were one of the clearest sources of inspiration for the ABLE Workflow. They show that a project does not have to begin as a pile of scripts and notebooks that slowly accumulates structure by accident. A good template can make repository layout, packaging, documentation, and workflow conventions easier to teach and easier to repeat.

A first group is the family of **data and research project templates**. Projects such as [Cookiecutter Data Science](https://cookiecutter-data-science.drivendata.org/), [NLeSC/python-template](https://github.com/NLeSC/python-template), [DiamondLightSource/python-copier-template](https://github.com/DiamondLightSource/python-copier-template), and [pyOpenSci/pyos-package-template](https://github.com/pyOpenSci/pyos-package-template) helped establish the idea that a project should start with a recognizable shape instead of growing from ad hoc scripts and notebooks. Those projects are especially strong on directory layout, packaging, documentation, and contributor ergonomics. They make it easier for teams to agree on where code, data, tests, and reports belong. But many such templates stop short of fully specifying a file-based workflow engine, tabular data contracts, or a clean path from local development to shared compute environments. The ABLE Workflow takes inspiration from their clarity and approachability while pushing further into workflow execution, schema validation, and cross-environment reproducibility.

Within that group, [Cookiecutter Data Science](https://cookiecutter-data-science.drivendata.org/) and [cookiecutter-data-snake](https://github.com/martibosch/cookiecutter-data-snake) are especially useful because they show how much a template can do before a workflow engine is even involved. The official [Snakemake workflow template](https://github.com/snakemake-workflows/snakemake-workflow-template) and [nf-core](https://nf-co.re/docs/nf-core-tools/pipelines/create) push further by making the workflow itself more explicit and reproducible from the start. Together, these examples helped shape the idea that the ABLE Workflow should not just scaffold files, but scaffold an executable workflow, a usable package boundary, and a project structure that is easier to maintain over time.

## Real Snakemake workflows with reusable lessons

Real Snakemake workflows were just as important as template examples. They show what happens when reproducibility, HPC execution, domain-specific transformations, and ordinary development needs all meet in one repository. They also reveal which engineering practices are worth baking into a template because they repeatedly prove useful in real projects.

Projects such as [proj-mutator-mapping](https://github.com/quinlan-lab/proj-mutator-mapping), [CapCruncher](https://github.com/sims-lab/CapCruncher), and [SeqNado](https://github.com/Milne-Group/SeqNado) that are not templates at all but still matter as inspiration. These projects are valuable because they show what good practice looks like under real constraints: high-performance computing, shared clusters, large flat-file datasets, domain-specific transformations, and the need to publish code that others can inspect or rerun. Some of these projects combine workflow orchestration with validation libraries, some emphasize HPC deployment, and others demonstrate strong open-source engineering around a domain workflow. They are useful not because the ABLE Workflow should imitate them line for line, but because they reveal which pieces tend to be missing when a workflow grows organically. The ABLE Workflow tries to bake more of those hard-won lessons into the starting point.

## What the ABLE Workflow is trying to bring together

Across open-source and academic workflows, there is still a noticeable gap between what is possible and what is routinely adopted. Many projects still rely on long scripts, notebooks that cannot be rerun end to end, or workflow steps whose true dependencies live only in a developer's memory. Even strong codebases often leave key decisions implicit: which environment should run which step, how intermediate data should be validated, how outputs should be consumed downstream, or how another contributor should know whether they broke something.

The ABLE Workflow is shaped by the idea that these pieces should reinforce one another instead of being added later as isolated upgrades. It brings together a recognizable project structure, an executable workflow, reusable Python packaging, explicit tabular data contracts, automated checks, and a path that works across local machines and shared compute environments. The goal is not to maximize features. It is to make the important parts of a reproducible workflow easier to start with, easier to maintain, and easier to share.

## Why this page matters

Taken together, these examples suggest that strong analytical workflows are rarely the result of a single tool or convention. They emerge when project structure, workflow execution, packaging, validation, testing, environments, and documentation reinforce one another instead of being added piecemeal.

That is the baseline the ABLE Workflow is trying to make easier to start with, easier to maintain, and easier to share.
